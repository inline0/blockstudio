# WPML

WPML translates the attributes of a custom block only as far as a language
configuration file declares them. Blockstudio stores every field value in the
block comment under `blockstudio.attributes`, so each block needs an entry that
points WPML at its text fields. The `wp bs wpml config` command writes these
entries for every registered block.

## Why blocks need a configuration

WPML reads the configuration from a file named `wpml-config.xml` in the root
folder of the active theme and of each active plugin. For a must-use plugin
that is a single file, the folder has the name of the file without `.php`. See
[Language Configuration Files](https://wpml.org/documentation/support/language-configuration-files/)
and [Make Custom Gutenberg Blocks Translatable](https://wpml.org/documentation/support/language-configuration-files/make-custom-gutenberg-blocks-translatable/).

A block without an entry is left to WPML's automatic string detection, which
offers every string attribute of the block for translation. For a Blockstudio
block that includes select values, file references, URLs, and CSS classes.
Translators see these technical values next to the real text, and a translated
select value or class can break the block.

## Generate the configuration

Print the configuration and save it in the root folder of the theme or plugin
that ships the blocks:

```bash
wp bs wpml config > wp-content/themes/my-theme/wpml-config.xml
```

Or let the command write the file:

```bash
wp bs wpml config --file=wp-content/themes/my-theme/wpml-config.xml
```

A block with a text field, a link, and a repeater:

```json title="block.json"
{
  "name": "my-theme/cards",
  "title": "Cards",
  "blockstudio": {
    "attributes": [
      { "id": "heading", "type": "text", "label": "Heading" },
      {
        "id": "style",
        "type": "select",
        "label": "Style",
        "options": [
          { "value": "light", "label": "Light" },
          { "value": "dark", "label": "Dark" }
        ]
      },
      {
        "id": "cards",
        "type": "repeater",
        "label": "Cards",
        "attributes": [
          { "id": "title", "type": "text", "label": "Title" },
          { "id": "image", "type": "files", "label": "Image" },
          { "id": "link", "type": "link", "label": "Button" }
        ]
      }
    ]
  }
}
```

becomes:

```xml title="wpml-config.xml"
<wpml-config>
	<gutenberg-blocks>
		<!-- blockstudio:start -->
		<!-- Generated by wp bs wpml config. Run it again after changing block fields; edits between the markers are replaced. -->
		<gutenberg-block type="my-theme/cards" translate="1" label="Cards">
			<key name="blockstudio">
				<key name="attributes">
					<key name="heading" label="Heading" />
					<key name="cards">
						<key name="*">
							<key name="title" label="Cards: Title" />
							<key name="link">
								<key name="title" label="Cards: Button" />
								<key name="url" type="link" label="Cards: Button: URL" />
							</key>
						</key>
					</key>
				</key>
			</key>
		</gutenberg-block>
		<!-- blockstudio:end -->
	</gutenberg-blocks>
</wpml-config>
```

The `style` and `image` values are not declared, so WPML copies them into the
translation unchanged.

## What is declared

The command reads the registered blocks, after `custom/` fields and block fields
are expanded and overrides and attribute filters are applied. Fields that
[extensions](/docs/extensions) add to a Blockstudio block are included. Fields
that extensions add to core blocks or to blocks of other plugins are not, because
those blocks get their configuration from WPML or from their own plugin.

| Field | Declaration |
| --- | --- |
| `text`, `textarea`, `richtext`, `wysiwyg` | Translatable text. |
| `link` | `title` as text and `url` with `type="link"`, so WPML replaces a link with its translation when one is available. |
| `repeater` | A level named `*` that matches every row, with the declarations of the row fields. Nested repeaters work the same way. |
| `group` with an `id` | The fields of the group, with the group ID as key prefix (`cta_text` for the field `text` in the group `cta`). |
| `group` without an `id`, `tabs` | The fields, without a level of their own. |
| Every other built-in type | Not declared. WPML copies the value unchanged. |

A block without a declared field gets `translate="0"`. WPML then copies all of
its values and offers nothing from it for translation. Inner blocks are
translated as usual.

Not declared:

- Fields with `hidden`, because their values are not written by editors.
- Fields of [custom field types](/docs/blocks/attributes/custom-field-types).
  The command prints a warning for each, because only the field type knows
  whether its value holds text.
- Attributes that a block declares in its native `attributes` instead of as
  Blockstudio fields.
- Storage keys whose fields have different types, see below.

Every text field is declared, including one that holds a technical value such
as a CSS class.

The `label` of each key is the field label, preceded by the labels of the
enclosing repeaters and groups with an ID. WPML shows it as the field name in
the translation editor.

### Fields with the same storage key

Two fields can end up with the same storage key, for example a block field and
an extension field with the same `id`, or the field `text` in a group with the
ID `cta` and a field with the ID `cta_text`. The command declares such a key
only when it is clear what is stored there:

- Within the fields of a block, outside repeater rows, Blockstudio registers
  one attribute per storage key, so a later field replaces an earlier one,
  whatever its type. The fields
  of the extensions of a block work the same way: a later field, or the field
  of an extension registered later, replaces an earlier one.
- A block field and an extension field with the same key both stay in effect.
  The block template receives the value as the block's field defines it, while
  the extension is applied with its own field. The key is declared once when
  both fields need the same
  declaration: both are text fields (`text`, `textarea`, `richtext`, or
  `wysiwyg`), both are links, or neither is declared, such as a `select` and a
  `number`. Two repeaters are compared field by field in their rows. The label
  comes from the block's field.
- Two fields with the same `id` in the rows of one repeater both stay in effect
  as well, and are compared the same way.

When the types differ, for example a `text` field in the block and a `select`
in an extension, the stored value is text or a select option, depending on the
control that wrote it. The command does not declare the key and prints a
warning:

```bash
Warning: Not declared, the fields that store this key have different types: my-theme/cards: tone (text in the block, select in an extension)
```

Rename one of the fields, or give both the same type, to have the key declared.

## Keep the configuration up to date

Run the command again after adding, removing, or renaming fields, and ship the
updated file with the theme or plugin. Content that existed before shows new
fields for translation once its original is updated, as described in the WPML
guide above.

With `--file`, the command creates a missing file. In an existing file, it
replaces only the text between `<!-- blockstudio:start -->` and
`<!-- blockstudio:end -->`, so other sections and entries for other blocks stay
as they are:

```xml title="wpml-config.xml"
<wpml-config>
	<custom-types>
		<custom-type translate="1">book</custom-type>
	</custom-types>
	<gutenberg-blocks>
		<gutenberg-block type="my-plugin/map" translate="1">
			<key name="caption" />
		</gutenberg-block>
		<!-- blockstudio:start -->
		<!-- blockstudio:end -->
	</gutenberg-blocks>
</wpml-config>
```

To use an existing file that has no markers yet, add the two marker lines once
inside its `gutenberg-blocks` element, or add a `gutenberg-blocks` element with
the markers if the file has none. Without the markers, or when the result would
not be a valid configuration, the command leaves the file unchanged and exits
with an error.

Entries for Blockstudio blocks that were written by hand, such as
`translate="0"` entries that hide technical values, are no longer needed once
the generated section covers the block. The command warns about every block
that is declared more than once, so these entries can be removed.

## Image texts in translation jobs

WPML puts the texts of the images that a page uses into the translation job of
the page: title, alt text, caption, and description. When the job is
completed, WPML writes the translated texts to the attachment of the target
language and creates that attachment if there is none yet. See
[How to Translate Media](https://wpml.org/documentation/translating-your-contents/media/).
WPML finds the images in `<img>` tags in the content, in galleries, in the
featured image, and in the blocks it knows. A Blockstudio block stores
attachment IDs in the block comment, so WPML finds none of them.

When WPML is active, Blockstudio adds the attachments that its fields store in
the blocks of a page to the images WPML found:

- `files` fields, including hidden ones, and `attributes` fields with `media`,
  the same fields the block editor loads as media.
- Fields in groups, tabs, repeater rows, and inner blocks.
- Fields of [extensions](/docs/extensions), also on core blocks and blocks of
  other plugins, because their values are stored in the attributes of the
  extended block.

Values that are not the ID of an attachment are left out. Nothing needs to be
configured, and the `wpml-config.xml` is not involved. Without WPML, nothing is
loaded.

The texts are part of the job only when one of the image text options under
WPML > Settings > Media Translation is enabled, "Automatically detect best
options for translating image texts" or "Translate Media Library texts when
translating content", as for images in core blocks.

Blockstudio reports the images through the filter
`wpml_ids_of_media_used_in_post`, which WPML applies to the media of a post in
`PostWithMediaFiles`. To leave an image out of the jobs, remove its ID in a
callback on the same filter with a priority above 10:

```php
add_filter(
	'wpml_ids_of_media_used_in_post',
	function ( $ids ) {
		return array_values( array_diff( $ids, array( 42 ) ) );
	},
	20
);
```
